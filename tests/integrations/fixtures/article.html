Why the audio callback must never block

By Bozhidar Ivanov

20 October 2026

Every audio API hands you a callback that runs on a real-time thread. The device fills a buffer every ten milliseconds or so, and if your code is not finished when the next buffer arrives you hear a glitch. That is the whole contract: do your work in less time than the buffer represents, every single time.

The tempting shortcut is to do a little work in the callback: resample, run the voice activity detector, maybe append to a Python list under the GIL. Each of those can take an unbounded amount of time on a bad day, and a bad day is exactly when users notice.

Push, do not process

The rule we settled on is that the callback only copies frames into a lock-free single-producer single-consumer ring buffer. Nothing else. A worker thread drains the ring buffer, runs the models and pushes events into a queue that Python polls.

Dropped samples are counted and reported, never silently lost.

Counting drops matters because it turns an invisible failure into a number on the dashboard. If the worker falls behind, the count climbs and we know to look.

  • The callback never allocates, locks or logs.
  • The worker owns every model and every allocation.
  • Python learns about events by polling, never by callback.
